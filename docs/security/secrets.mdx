"Secrets that can't leak" is a real guarantee with a precise shape. This page describes exactly how it works and, just as important, what it does and does not protect against. For the configuration surface like binding secrets, allow lists, and placeholders, see [Secrets](/sandboxes/secrets).

## The idea

Instead of putting a real credential inside the VM, microsandbox puts a **placeholder** there. The real value stays in host memory. When the guest sends a request to a host you've allowed, the host-side network stack swaps the placeholder for the real value at the network boundary, on the way out. Anywhere else, the placeholder is just a meaningless string.

So a workload can call an API with a credential it never actually holds.

## The data flow

1. You bind a secret to an environment variable and list the hosts it's allowed for.
2. The guest's environment receives a placeholder (`$MSB_<env_var>` by default), never the real value.
3. The workload uses the placeholder as if it were the credential, in a header, auth field, query string, or body.
4. On egress to an allowed host, the host-side proxy decrypts the intercepted TLS, verifies the request is really going where it claims, substitutes the real value, and forwards it upstream.
5. The upstream server receives the real credential. The guest never did.

## What gates a substitution

A placeholder only becomes a real value when **every** one of these holds. They use the same DNS and SNI machinery the [network page](/security/network#dns-to-ip-binding-toctou) describes:

- **Allowed-host match.** The TLS SNI matches one of the secret's allowed host patterns.
- **DNS pin.** The destination IP was actually resolved for that host through the interceptor, so a hard-coded IP with a forged SNI doesn't qualify.
- **TLS identity.** By default a secret requires intercepted TLS, so it is never substituted over a connection the host can't see into.
- **Authority alignment.** For intercepted HTTP, the request's `Host` or `:authority` must match the SNI, which closes domain-fronting.

If any check fails, the placeholder is left untouched. The request goes out carrying a useless string, or it's blocked, depending on your policy.

## What this protects

- **The credential cannot leak to a host you didn't allow.** Send the placeholder to `evil.com` and `evil.com` receives the placeholder, not the secret.
- **A captured guest is worthless for the secret.** A memory dump, a leaked image, or a malicious process inside the VM will only ever find the placeholder.
- **Hard-coded-IP and SNI-spoof exfiltration attempts** don't receive the injection at all, because they fail the DNS pin or authority checks.

## What this does not protect

Being candid about the edges matters more than the headline.

- **The allowed endpoint receives the real credential.** This stops exfiltration to *other* hosts. It does not stop the host you explicitly allowed from misusing what you sent it. Keep allow lists narrow.
- **It needs TLS interception for that host.** Over a bypassed-TLS domain, or plain HTTP with the default TLS-identity requirement on, no substitution happens. That's by design, since the host can't verify where opaque traffic is really going. You can opt a secret into plain-HTTP injection, but it's weaker and not recommended.
- **A few content shapes aren't rewritten.** Placeholders inside HTTP/2 request bodies, non-identity-encoded (for example gzipped) bodies, or very large fixed-length bodies aren't substituted. When an injection is eligible but can't be substituted safely, the request is blocked rather than sent wrong.
- **Real values live in host process memory.** They're held as plain strings for the sandbox's lifetime and aren't specially zeroized. Anyone who can read the host process's memory is already on the trusted side of the boundary, and [host compromise is out of scope](/security/overview#scope-what-the-boundary-covers) for the model.

## Where the values live

Real secret values exist only in the host process, only for the sandbox's lifetime. They are never written to the guest's environment, the guest's disk, or a snapshot. When the sandbox stops, they're gone.

## Origin-scoped header credentials

A **header credential** is a second credential model, alongside placeholder
substitution. Where a placeholder substitutes a value the guest already sent, a
header credential **sets** one named request header to a formatted secret value
on requests to exactly one HTTPS origin. The guest need not send anything, and
the value can never be steered into another field.

It is aimed at host-held credentials — for example an API key in an OS keychain
the embedding application can read but does not want to write to any file.

### Two types: durable rule, launch-only value

A header credential splits into two types that are **not** interchangeable:

- The durable rule (in `SandboxConfig` / `SecretsConfig`) carries only
  non-secret authorization metadata: an `id`, a **reference** the host resolver
  understands, the exact `HttpsOrigin`, the header name, and a `format` template
  with exactly one `%s`.
- The resolved value is a separate, internal launch-only type. It exists only on
the private, memory-backed config FD and in the runtime's memory.

The value is supplied at spawn time by a `CredentialResolver` the embedding
application passes **per launch** (`Sandbox::create_with_pull_progress_and_resolver`
et al.). It is not a process-global registration. Only bytes cross the `fork`;
no trait object does.

```rust
use std::sync::Arc;

use microsandbox::{CredentialResolver, CredentialResolveError, Sandbox, SandboxConfig};

/// Values come from the host keychain; only their non-secret references are
/// ever persisted.
struct KeychainResolver;

impl CredentialResolver for KeychainResolver {
    fn resolve(
        &self,
        reference: &str,
    ) -> Result<zeroize::Zeroizing<String>, CredentialResolveError> {
        // `reference` is the non-secret name stored in the durable config;
        // look the value up in your keychain / secret store here.
        lookup_local_keychain(reference)
            .map(zeroize::Zeroizing::new)
            .map_err(|_| CredentialResolveError::not_found())
    }
}

// Durable config: only the non-secret authorization rule.
let config: SandboxConfig = builder
    .network(|network| {
        network.header_credential(|credential| {
            credential
                .id("anthropic")
                .reference("anthropic-api-key")
                .origin("api.anthropic.com", 443)
                .header("x-api-key")
                .format("%s")
        })
    })
    .build()
    .await?;

// Per-launch resolver: two concurrent creates cannot observe each other's
// values, and nothing is registered process-wide.
let (progress, task) = Sandbox::create_with_pull_progress_and_resolver(
    config,
    Arc::new(KeychainResolver),
);
drop(progress); // or consume pull events until the channel closes
let sandbox = task.await??;
```

A stopped or crashed reference-backed sandbox cannot be restarted by name (it
has nowhere to receive a resolver): recreate it with the resolver instead.

### What gates injection

A credential is set only when **all** hold:

- the connection is TLS-intercepted (never on a bypass or plain HTTP);
- the SNI matches the credential's origin host;
- the destination identity is verified: on direct TLS the guest's destination IP
  must be bound to that host by the live DNS cache (a matching SNI pointing at
  another IP injects nothing), while a CONNECT-tunnelled connection uses the
  proxy-verified CONNECT authority instead;
- the guest destination port equals the credential's origin port;
- the request's `Host` / `:authority` host **and** port equal the origin (an
  absent port means 443);
- an absolute-form request target agrees with the authority and uses `https`;
- `:scheme`, when present, is `https`.

A well-formed request to an unapproved origin is **forwarded without
injection**, not blocked. The existing `Host`/`:authority`-versus-SNI identity
rejections are unchanged and still block.

### No filesystem plaintext

The config FD is Linux `memfd_create` or an anonymous macOS/other-Unix pipe; the
plaintext is never written to a filesystem-backed temporary file, the durable
config, the sandbox database, or argv. It is also never put in a log line,
error message, `Debug` or `Display` **by this feature's own code paths**: the
credential-specific errors carry only an index and fixed labels, and the
resolved type redacts every field. Unrelated pre-existing log lines that print
caller-controlled metadata (for example the sandbox name) are not covered by
that claim. Values are held in `Zeroizing` buffers.

This is an **application-level** guarantee: it covers what the application
explicitly persists. It does **not** cover OS paging/swap of ordinary memory or
memfd pages, core/crash dumps, hibernation, or same-uid `ptrace`/FD inspection.
The host OS and other same-uid processes are inside the trust boundary.

### Lifecycle and limits

- **Rotation is launch-scoped.** The value is resolved once, at spawn. A
  host-side rotation does not reach a running sandbox; recreate it to pick up a
  new value.
- **Restart by name is refused.** `Sandbox::start` / `start_detached` refuse a
  reference-backed sandbox (`RestartRequiresResolver`) before any state change,
  because they have nowhere to receive a resolver. Recreate with a resolver.
- **A failed resolution can leave a stopped record.** The durable record is
  written before the resolver runs, so a resolver failure (or an unsafe value)
  fails the create but can leave a `Stopped` record carrying the reference only
  — never a value. Recreate it, or remove it, explicitly.
- **Local only.** Header credentials are rejected on the cloud backend and on
  Windows, before any database mutation.
- **Capability preflight.** The embedding application probes the installed `msb`
  for the fixed `header-credential-launch-v1` token before a credential-bearing
  create and again before the resolver runs, so an older runtime cannot silently
  ignore the field. This is a **compatibility** guard, not an atomic
  anti-tampering check: it does not compare file identity between the probe and
  the exec, so a same-uid process that replaces the binary in between is outside
  the trust boundary this feature defends.
