weekly pages, which upstream owns; this page is the fork's own changelog and is the place new
fork-only entries belong.

## File-backed (rotating) secrets

Secrets can be bound to a host file instead of an environment variable. The network engine
re-reads the file for every eligible connection, so rotating the credential on disk
(`echo -n new-token > /run/creds/token`) takes effect on the next connection with no `msb modify`
call and no sandbox restart. Only the file path is stored in the durable sandbox config; the bytes
are never persisted, logged, or sent to the guest. A missing, unreadable, symlinked, oversized
(over 64 KiB), empty, or non-UTF-8 file fails closed: the placeholder is blocked in the secret's
substitution locations for that connection, even under a `Passthrough` violation policy for the
host.

```yaml
TOKEN:
  value:
    $msb_file: /run/creds/token
  allow: ["api.example.com"]
```

See [Secrets](/sandboxes/secrets#file-backed-rotating-secrets).

## Origin-scoped header credentials

A header credential **sets** one named request header on requests to exactly one HTTPS origin,
where a placeholder substitutes a value the guest already sent. The durable config carries only a
non-secret authorization rule plus a reference; an embedding application passes a
`CredentialResolver` per launch, and the resolved value travels only on the private memory-backed
launch-config fd — never to the durable config, the database, argv, or a log line.

```yaml
network:
  secrets:
    header_credentials:
      - id: anthropic
        reference: anthropic-api-key
        origin: { host: "api.anthropic.com", port: 443 }
        header: "x-api-key"
        format: "%s"
```

The origin's port must be TLS-intercepted (port `443` by default); a credential on a port that is
not intercepted is refused at configuration time rather than silently never injected. The
installed `msb` must advertise the `header_credentials` capability in `msb __launch-protocol`
before a credential-bearing create, so an older runtime cannot silently ignore the field.

See [Header credentials](/security/secrets#origin-scoped-header-credentials).

## Fail-closed request interception

TLS-intercepted traffic can be checked against a host-run hook before it reaches upstream. A rule
matches a request by SNI host, HTTP method, and path prefix; the hook decides whether to forward,
rewrite, or refuse it, and a request on a policed host that matches no rule is refused rather than
forwarded — never sent upstream with a substituted credential and no policy applied.

```yaml
network:
  intercept:
    hook: ["/usr/local/bin/intercept-hook"]
    rules:
      - { host: "api.github.com", method: "GET", path_prefix: "/repos/" }
```

When interception is active, both the guest-facing certificate and the upstream connector pin
ALPN to `http/1.1`, so HTTP/2-capable clients and servers downgrade cleanly instead of sending
framing the interceptor's HTTP/1.1 parser can't read. Note that an `intercept` config with
`tls.enabled = false` is inert: interception runs inside the TLS-intercepting proxy.

See [Request interception](/sandboxes/intercept).

### TLS without SNI

Interception requires a `ClientHello`, not a server name. A guest that connects to a literal IP
address (or otherwise sends no SNI) is still accepted, with its identity taken from the destination
IP: no DNS-origin material exists, so header credentials — which are origin-scoped by host name —
are never applied on that route, while placeholder substitution may still be applied by a wildcard
(`HostPattern::Any`) or IP-based secret policy. For the same reason a hostname intercept rule does
not match an IP route; an exact-IP rule does.

## Opt-in ambient host proxy discovery

A local sandbox can opt into discovering an HTTP `CONNECT` proxy from the host proxy environment
(`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, and their lowercase spellings) at each network
start, so a machine behind a corporate proxy reaches the network without pinning an endpoint per
sandbox. It is **off by default** and does not enable networking on its own.

```bash
msb run python --proxy-from-env          # or --proxy-from-env=false, proxy_from_env: true, MSB_PROXY_FROM_ENV=1
```

Only the enablement boolean is stored. The selected endpoint, its URL credentials, and the bypass
rules stay in host memory and are never serialized into sandbox configuration or the guest
environment. An explicit upstream [`outbound_proxy`](/networking/outbound-proxy) (HTTP `CONNECT`,
SOCKS4, or SOCKS5) wins and is used without reading any host proxy variable. `NO_PROXY` bypasses a
destination; once a proxy is selected, a proxy failure does not retry the origin directly. Non-DNS
UDP cannot travel over `CONNECT` and is dropped while ambient routing is selected.

See [Proxies](/networking/outbound-proxy#discover-a-proxy-from-the-host-environment) and
[Ambient host HTTP proxy](/networking/overview#ambient-host-http-proxy).

## Auto-published guest listeners

A sandbox can mirror its guest TCP `LISTEN` sockets onto host listeners, Lima-style.

```yaml
network:
  auto_publish: true   # or: { poll_interval_ms: 2000, host_bind: "127.0.0.1" }
```

Host listeners appear as the guest binds and disappear when it closes them, and the SDK can
observe the same events through `Sandbox::port_events`.

Auto-publish needs this build's generation-11 guest agent. A restored pre-sync memory snapshot keeps
the older guest agent it captured, so its listeners are never published; restore it as a
disk-only sandbox, or recreate it.

See [Auto-published listeners](/networking/overview).

## Interactive attach input filter (Rust SDK)

`AttachOptionsBuilder::stdin_filter` installs a `StdinFilter` that sees each chunk of terminal
input after the detach-key scan and returns the bytes to forward. It can pass them through,
rewrite them, or drop them. The filter runs on its own task, one chunk at a time and in input
order, so the attach loop can keep draining guest output while it waits on the guest (for example,
writing a file with `fs().write()` before letting a key through). This is the API guarantee of the
task boundary, **not** a claim that end-to-end liveness has been verified on every backend: local
combined-port relay behavior is the only traced coupling; dual-port and cloud are unverified, and
Windows interactive filtering is not yet exercised by an automated test.
Ordinary failures and timeouts inside `filter` are entirely caller-owned: the trait returns
`Vec<u8>`, not `Result`, and the SDK applies no timeout. A filter that can fail should bound
its own work and return the original bytes as its fallback. An unwinding filter panic ends
the attach session with `Runtime("stdin filter task ended")`; the guest may keep running as
after detach. With `panic = "abort"`, no policy can intercept the process exit. With no
filter set, attach behaves exactly as before.

See [`AttachOptionsBuilder::stdin_filter()`](/sdk/rust/execution#attach_options-stdin_filter).

## Live network policy replacement

A running local sandbox's policy can be replaced over the live control endpoint, with no restart
and no lost work. `Sandbox::update_network_policy` returns the new policy revision; the launch
policy is revision `1`. Decisions made after the call returns — DNS queries, new flows, and new
connections — see the new revision, while a TCP connection that was already admitted keeps the
policy it was admitted under, including its per-request plain-HTTP secret authority checks. A
`CONNECT` tunnel through such a connection keeps working too: the strict `CONNECT` check only
applies the opaque-hostname restriction and never re-authorizes the tunnel's target, so a
replacement does not close a tunnel. UDP
datagrams and ICMP echoes are evaluated per packet, so a revoke reaches the next datagram and does
not cut an established UDP session. The `multi-tenant` platform floor is a separate fixed policy
and cannot be relaxed this way, and the replacement is not persisted: restart, restore, and fork
start again from the launch policy at revision `1`.

```rust
use microsandbox::NetworkPolicy;

let policy = NetworkPolicy::builder()
    .default_deny()
    .egress(|e| e.tcp().port(443).allow_domains(["api.example.com"]))
    .egress(|e| e.udp().tcp().port(53).allow_host())
    .build()?;

let revision = sb.update_network_policy(policy).await?;
```

The runtime advertises `network_policy_update` in capability discovery, and the SDK refuses
before sending when it is absent, returning `Unsupported` instead of reporting a fault so a
launcher can offer a next-launch grant. This is the Rust SDK only: there is no `msb` command and
no Python, Node, Go, or Ruby method.

See [Replacing a running sandbox's policy](/networking/overview#live-policy-replacement).

## Egress refusal log

A local sandbox with networking enabled writes one JSON line to `<sandbox-dir>/logs/network.log`
for every egress decision it refuses, at the moment it refuses it. A refusal is recorded by a policy
or by the `multi-tenant` platform floor, by the strict-hostname rule, by DNS rebind protection, by
protocol-steering drops such as QUIC blocking and alternative-DNS or DNS-over-TLS ports, by the
secrets handler's authority and header-limit checks, by a secret violation, and by the fail-closed
proxy path. Capacity refusals, malformed-input blocks, allowed flows, and ingress denials are not
recorded, and neither are the `403` and in-tunnel TLS denial responses: they present a decision that
was already recorded where it was made.

Each record reports facts only — the site that refused, whether the sandbox policy or the floor owns
the decision, the destination the guest used, the guest-supplied name evidence and its source, and
the policy revision in force. Classifying refusals and coalescing them are the launcher's job. The
file rotates like `exec.log` (10 MiB, `.1` to `.4`), each site's own token bucket caps it at a
256-record burst and 20 records/s with a `suppressed` record carrying the count, and it is removed
with the sandbox.

```rust
use futures::StreamExt;
use microsandbox::logs::{LogSource, LogStreamOptions, NetworkLogRecord};
use microsandbox::Sandbox;

let sb = Sandbox::get("egress").await?;
let mut refusals = sb
    .log_stream(&LogStreamOptions {
        sources: vec![LogSource::Network],
        follow: true,
        ..Default::default()
    })
    .await?;

while let Some(entry) = refusals.next().await {
    let record: NetworkLogRecord = serde_json::from_slice(&entry?.data)?;
    println!("{record:?}");
}
```

One refused TCP SYN:

```text
{"v":1,"t":"2026-11-05T14:03:07.412Z","s":"network","event":"refusal","site":"tcp-syn","layer":"tenant","protocol":"tcp","dst_ip":"203.0.113.10","dst_port":443,"name":"api.example.com","name_source":"dns-cache","revision":2}
```

The `network` source is never in the default sources and never in `msb logs --source all`, and the
Python, Node, Go, and Ruby SDKs do not accept it. A newer SDK that requests the `network` source
from a runtime that predates it gets an empty stream rather than an error: there is no capability
bit for it, because a stopped sandbox's logs are read directly with no runtime to query. A writable
bind mount of a sandbox's own directory is refused at launch so the guest cannot rewrite its own
log; a writable bind of a parent directory is still allowed and exposes that log.

This is the Rust SDK only: there is no new `msb` command — `msb logs --source network` reads the
file.

See [Refusal log](/networking/overview#refusal-log).

## Placeholder refusals follow the substitution scope

A secret placeholder is now refused only in a location where that secret could have been
substituted. A placeholder in a header or body location its secret does not substitute in — for
example a headers-only credential's placeholder quoted in a request body — reaches any host
unchanged, and the forward is neither logged nor recorded as a refusal. A placeholder in an enabled
location, in the URL path or query string, or in a stream that is not HTTP still follows the
violation action. Nothing is substituted anywhere new: the forwarded bytes are the marker, never
the credential.

This fixes sessions that quote a placeholder into every request body, such as an agent transcript
that once ran `env`, which a foreign host used to answer with `403 Request blocked by secret
policy.`

See [Violation actions](/sandboxes/secrets#violation-actions).

## Attributed credential refusals

A secret-policy `403` now says which credential was refused, where its placeholder was, to which
host, and why, in `message` — the one field a client such as Claude Code shows — and in three
value-free envelope fields: `credential` (the secret's environment variable name), `location`
(`header`, `basic-auth`, `trailer`, `query`, `unknown`, `body`, `chunk-metadata`) and `reason`
(`host-not-covered`, `credential-unavailable`, `destination-unverified`). A configured
`secret_deny_message` is now appended verbatim after that facts sentence instead of replacing the
message, and an unset or empty one leaves the facts sentence alone.

The reason is the one that, fixed, would let the request through: restoring an unreadable
file-backed secret is reported as `credential-unavailable` only when a readable file would have
been substituted or passed through, and every other mismatch reports the destination. The same
three fields reach each `secret-violation` refusal record in `network.log`, so a launcher can show
them later. A name that itself contains a placeholder is never stated: the field is omitted and
the sentence says "a credential".

```json
{
  "code": "secret_policy_denied",
  "message": "Blocked: MSB_ANTHROPIC_KEY was sent in a request header to api.deepseek.com; it is substituted only for api.anthropic.com.",
  "domain": "api.deepseek.com",
  "credential": "MSB_ANTHROPIC_KEY",
  "location": "header",
  "reason": "host-not-covered"
}
```

See [HTTP denial responses](/networking/overview#http-denial-responses) and
[Refusal log](/networking/overview#refusal-log).
